# CD audit — 2026-09-30

Goal restated: an agent runs one command, the user types a short code on
their phone (or does nothing at all), and the file arrives **as fast as the
network allows**. Speed first, everything else second.

## Measured baseline (production, from India)

| Measurement | Result |
| --- | --- |
| Cloudflare edge serving this machine | `colo=MRS` (Marseille), 148 ms RTT |
| Raw upload to Cloudflare | 2.14 MiB/s |
| Raw download from Cloudflare | 4.67 MiB/s |
| `cd send` → code printed | 1.54 s |
| 100 MiB `cd send` → `cd receive` (same machine) | 54 s = **1.85 MiB/s** |
| Sender exit status on CLI→CLI runs | **1 of 4 runs exited 1** ("receiver disconnected") although the receiver saved identical bytes |

What that means: the relay code itself isn't the bottleneck. It uses about 86%
of the upload link. The design is: every byte goes phone → Marseille → phone,
even when both devices sit on the same Wi-Fi. A LAN path would be 10–50× faster
on the same hardware. No amount of relay tuning gets there.

## Benchmarks (`npm run bench`)

`npm run bench` builds the CLI and reports time to code, CLI→CLI relay
throughput, and browser→browser P2P and relay-fallback throughput, all with
byte-exact checks. It runs against local `wrangler dev` by default, or a
deployed Worker with `CD_VERIFY_URL`. Local runs go over loopback, so they
measure protocol and CPU overhead, not the network.

| When | Target | Code (median) | Relay CLI→CLI | P2P browser | Relay fallback |
| --- | --- | --- | --- | --- | --- |
| Baseline (P0 fixes only) | local, 64 MiB | 24 ms | 19.7 MiB/s | 17.5 MiB/s | 9.3 MiB/s |
| Baseline (deployed code) | cd.yash0.in, 16 MiB | 1,755 ms | 0.37 MiB/s | n/a | not deployed |
| Raw P2P channel, 16 MiB window (item 9) | local, 64 MiB | 20 ms | 19.7 MiB/s | 16.0–16.2 MiB/s | 10.4 MiB/s |

Item 9 A/B in one session, three runs each, 64 MiB, local: P2P before the
change 7.3 / 7.7 / 9.5 MiB/s; after 16.2 / 16.0 / 16.0 MiB/s (about 2×);
the PeerJS-framing path peers without raw-channel support still use is
7.0 MiB/s. The single 17.5 MiB/s baseline run above did not reproduce, so
treat it as an outlier. Local P2P is capped by the harness: raw
`RTCDataChannel` between two headless Chromium pages peaks at 35 MiB/s
(88 MiB/s within one page), so real devices on a LAN should do better than
these local numbers.

Raw link during the production run: upload 0.50 MB/s, download 4.1 MB/s
(`speed.cloudflare.com`), edge `MRS`. The link was slower than on the
original audit run (2.14 MiB/s up), so compare production rows only with
rows measured the same day.

## CD vs CDX

They are not two different backends. `cdx.yash0.in` (worker `cd-cdx`) is a
staging twin of `cd.yash0.in` (worker `cd`) deployed from the same
`worker/index.ts`. `cdx` was the old CLI name. The working tree already folds
everything into `cd` (`cmd/cdx` → `cmd/cd`, the `env.cdx` block removed from
`wrangler.jsonc`, and installers delete stale `cdx` binaries). Remaining:

- The deployed `cd-cdx` worker at `cdx.yash0.in` is still live. Delete it with
  `npx wrangler delete --name cd-cdx` (needs confirmation, since it's outward-facing).
- Commit the uncommitted consolidation.
- `.gitleaks.toml` still names a `cdx/` path. Keep it, because gitleaks
  scans history, where that path still exists.

The binary name `cd` is a problem of its own (see Agent friendliness below).

## Scores

| Area | Score | Why |
| --- | --- | --- |
| Transfer speed | **3/10** | CLI and `/send` are relay-only; no LAN or direct path; hairpin via a distant colo; browser P2P uses PeerJS `binary` (BinaryPack) framing plus a 3 MiB receiver window. |
| Time to first code | **5/10** | 1.5 s: TLS WebSocket dial → join → `accepted` → *second* TLS connection for `POST /api/codes` → the directory lists **every** stored code before claiming. All sequential. |
| Reliability | **4/10** | False failures on CLI→CLI (the Go receiver hard-closes TCP right after `COMPLETE`). Browser P2P has no TURN and no fallback, so it fails on CGNAT/mobile data (Jio/Airtel). The relay aborts the whole transfer when the peer buffer passes 32 MiB, and there's no resume. |
| Agent friendliness | **4/10** | Good: one stdout line, `--json`, meaningful exit codes. Bad: the binary is named `cd`, so in any non-interactive agent shell `cd send x` runs the *builtin* unless shell-init was sourced. The sender must stay in the foreground for up to 15 min, which kills most agent tool calls (e.g. a 2-minute Bash timeout). The skill rebuilds with `make cd` on every send. |
| CLI UX | **5/10** | Clear errors, typo suggestions, `--out/--force`. One file only (no folders, globs or stdin), the name collides, no speed or ETA, no detach mode. |
| Browser UX | **5/10** | Two code systems: words (`river-mango`) for browser P2P and digits (`48291`) for relay, with different pages (`/`, `/send`, `/s/*`) and redirects between them. P2P fails silently on bad NATs. |
| Security | **6/10** | Link mode is solid: HKDF, AES-GCM, direction-separated nonces, and a receiver token hash. Code mode isn't E2E: the directory hands the master key to anyone with a 5-digit code. The 30/min/IP limit is weak against distributed guessing of 100k codes, and a lookup doesn't consume the code. The P2P word code (14,641 values) is only a rendezvous address, so the first peer to connect gets the file. |
| Architecture / code quality | **6/10** | The protocol is re-implemented three times (Go, JS, Kotlin). `src/main.js` is a 1,564-line monolith. `drainAcks` re-injects `COMPLETE` via a spawned goroutine (fragile). A single global `CodeDirectory` DO is a hot spot and scans O(n) per claim. |
| Scalability / cost | **5/10** | Relaying every byte through Durable Objects burns free-plan quota and pins throughput to one DO. The global code directory serialises every claim and lookup. |
| Tests / CI | **7/10** | Go and JS unit tests pass; real-Chromium e2e scripts (`verify:agent`, `verify:terminal`, `verify-p2p`); CodeQL; checksummed releases. No test catches the CLI→CLI completion race, and nothing benchmarks throughput. |
| Android app | **3/10** | Only speaks P2P word codes over PeerJS signaling, so it can't receive digit codes from `cd send`. No relay fallback, and its sender flow control is known-incomplete (see `docs/transport-options.md`). |
| Docs | **6/10** | Plenty of docs, but README, the highway docs and the code disagree on what's current. |

**Overall: 4.8 / 10.** The crypto is sound and the tests are good. The product
fails its own goal: it's slow because of the topology, flaky on phones, and
awkward for agents.

## Findings, ranked

### P0 — broken today

1. **False failure on CLI→CLI.** `cmd/cd/receive.go` sends `COMPLETE`, then
   `defer connection.Close()` drops TCP with no close handshake. The relay can
   deliver `peer-left` to the sender instead of `COMPLETE`, so the agent sees
   exit 1 for a delivered file. Fix: after `COMPLETE`, send a close frame and
   wait briefly for the peer or relay to close. On the sender, treat `peer-left`
   received after `END` plus a full ack as success-pending-verify only if we add
   a relay `delivered` event (see 6).
2. **Browser↔browser dies on CGNAT/mobile networks.** STUN only, no TURN, no
   fallback (`src/main.js` `peerOptions`). If ICE doesn't connect within about
   3 s, fall back to the relay room automatically.
3. **Binary named `cd`.** Agents and scripts can't call it reliably. Rename it
   (e.g. `cdrop`, `yd`, or keep `cdx` as the *binary* name), or at least make
   `cd` install a second, non-colliding alias.

### P1 — speed (the priority)

4. **Direct / LAN path for the CLI.** Embed WebRTC in the Go binary
   (`pion/webrtc`, pure Go, CGO-free). ICE picks, in order:
   same-LAN host candidates (tens of MB/s), a direct internet path via STUN,
   then the existing relay as fallback. The browser receiver already speaks
   WebRTC, so this unifies CLI and browser onto one transport. Expected win:
   same-Wi-Fi transfers limited by Wi-Fi (~20–60 MB/s) instead of your
   2 MiB/s uplink.
5. **Start sending before the receiver clicks.** Today: offer → wait for Accept
   → send. For a paired/trusted device, or with `--auto`, start streaming
   straight into staging and let Accept just rename. Saves a human round trip.
6. **Collapse time-to-code to one round trip.** Have the relay room mint the
   code as part of the sender `join` (the room calls the directory
   internally), or claim the code over the same WebSocket. Shard the directory
   by the code's first digit (10 DOs) and drop the `storage.list` scan (use
   alarms or TTL-keyed deletes). Target: under 400 ms from command to code.
7. **Relay placement.** Pass a `locationHint` (e.g. `apac`) when creating
   `TransferRoom`, chosen from the sender's `request.cf.continent`, so Indian
   users don't hairpin through Europe. Note: the `MRS` edge colo comes from ISP
   and plan routing; the DO hint only fixes the DO hop.
8. **Browser P2P framing.** Switch PeerJS `serialization: 'binary'` → `'raw'`
   (or drop PeerJS and use `RTCDataChannel` directly with our own 12-byte
   framing), use 256 KiB messages where supported, and raise
   `RECEIVER_WINDOW_BYTES` (3 MiB) to about 16 MiB on desktop. Currently a
   100 ms RTT caps it near 30 MiB/s before BinaryPack overhead.
9. **Relay chunk and window.** The relay isn't the bottleneck on this uplink,
   but on fast links an 8 MiB window over a ~300 ms sender→DO→receiver loop
   caps it at about 26 MiB/s. Make the window adaptive (grow until RTT rises).
   Replace the 32 MiB hard-kill with backpressure (stop reading from the sender
   socket) instead of aborting.

### P1 — agent friendliness ("zero tokens")

10. **`send --detach` (default when stdout isn't a TTY).** Fork a background
    holder, print the code, exit 0 immediately. `cd status` / `cd wait <code>`
    report the result. The agent spends one tool call and about 20 output
    tokens, with no long-lived shell, no timeouts, and no "don't wait"
    instructions.
11. **Paired devices = no code at all.** `cd pair` once (QR on the phone);
    afterwards `cd send file` pushes to "my phone" directly. The phone gets a
    notification and the file lands. This matches CONTEXT.md's
    *Trusted sender*. It's the actual end state of "my agent sends me files".
12. **Ship a skill that's one line.** Replace the 5-step SKILL.md with: *run
    `cd send <file>`; reply with the stdout line.* Drop `make cd` from the hot
    path (use the installed binary; build only in dev).
13. **Multi-file / folder.** `cd send a b dir/` streams a tar on the fly (or a
    manifest). Agents often need to send several artifacts.

### P2 — security and correctness

14. **Code-mode key custody.** Keep typability but get E2E back: derive the
    key with a PAKE (SPAKE2/CPace, as magic-wormhole does) from the short
    code, so the server never holds the key and each guess costs one online
    attempt. Burn the code after one failed attempt.
15. **Unify codes.** One digit code for everything. The receiver resolves it
    and the rendezvous negotiates WebRTC direct → relay. Retire the word
    codes, legacy 8/22-char codes, and the separate `/send` page.
16. **Sender hygiene.** Replace the `drainAcks` goroutine re-injection with a
    single state machine that consumes one inbound stream.

### P3 — structure

17. Split `src/main.js` into send, receive, transport and UI modules. Share
    protocol test vectors across Go, JS and Kotlin (one JSON vectors file) so
    the three implementations can't drift.
18. Add `npm run bench` covering relay and P2P throughput plus time-to-code,
    and gate regressions in CI. Speed is the product.

## Android app: is it worth it?

| Capability | Browser / PWA | Native Android app |
| --- | --- | --- |
| Receive with **zero taps** (agent pushes, file just appears) | No: the page must be open and foregrounded to receive | **Yes**: a foreground service receives in the background after a push (FCM or a persistent socket) |
| Notification "file from your agent" | Yes (Web Push to an installed PWA) | Yes |
| Save large files straight to Downloads | Partial: OPFS or blob on Android Chrome; no File System Access picker; big-file limits | **Yes**: MediaStore/SAF streaming, no size cap |
| Survive screen-off / app switch mid-transfer | **No**: Chrome throttles and kills background tabs | **Yes**, with a foreground service and wake lock |
| LAN speed (same Wi-Fi) | Yes via WebRTC host candidates (mDNS-masked, usually works) | Yes, plus a raw TCP/QUIC LAN path and NSD/mDNS discovery with **no internet** |
| Share-sheet "Send with CD" from any app | Limited (Web Share Target on an installed PWA only) | **Yes**, native |
| Auto-open / install APKs the agent built | No | Yes (with install permission) |
| Pairing, trusted devices, keys in secure storage | IndexedDB (clearable) | Android Keystore |
| Cost to build and maintain | Already exists | A third protocol implementation to keep in sync; Play Store or sideload friction |

**Recommendation:** make the browser flow fast and reliable first (items
1–9). Build Android only for the *paired-device, zero-tap* experience
(item 11). That's the one thing a browser can't do and the one that
matches "my agent just sends me files". When you do, make the app a thin
shell around the same WebRTC + relay protocol as the CLI (ideally sharing
code via gomobile from the Go implementation) instead of a third
hand-written protocol.

## Proposed order of work

1. P0 fixes: completion race, P2P→relay fallback, binary name. Small, and
   they unblock everything else.
2. `--detach` plus a one-line skill: the agent flow becomes one tool call.
3. Single-round-trip code minting plus a sharded directory: code in under 0.4 s.
4. pion/webrtc in the CLI with one unified code: LAN and direct speed.
5. Pairing plus push (PWA Web Push first, then decide on Android).
6. PAKE for code mode, multi-file, resume.

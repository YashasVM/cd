# Android and Linux background transfer feasibility

**Issue:** [#10](https://github.com/YashasVM/cd/issues/10)  
**Scope:** lifecycle, battery, offline LAN, internet fallback, durable resume, trusted recipients, and build/device validation.  
**Decision:** feasible for user initiated transfers and for a visibly running receiver; impossible to guarantee unattended offline reception after process death or Doze without an OS supported wake path. Treat that as a product limit and make the state explicit.

## Evidence from this checkout

The Android module is a Kotlin/Compose application with `minSdk 29`, `targetSdk 34`, Java/Kotlin 17, CameraX, bundled ML Kit barcode scanning, Infobip WebRTC, and a Java WebSocket client. Its manifest declares a `dataSync` foreground service, notification permission, `WAKE_LOCK`, and network permissions. The current service returns `START_STICKY` and acquires a 30-minute partial wakelock, but it does not own transfer state or restore a session after process recreation ([`TransferService.kt`](../../android/app/src/main/kotlin/in/yash0/cd/service/TransferService.kt)).

`MainActivity` starts that service when the repository enters waiting, connecting, transferring, or saving. The repository marks a connection gone as failed and has no protocol resume/checkpoint. The receiver streams bytes to MediaStore, which is the right shape for bounded memory, but a process death leaves the pending output and in-memory counters without a restart protocol ([`TransferRepository.kt`](../../android/app/src/main/kotlin/in/yash0/cd/transfer/TransferRepository.kt), [`FileSaver.kt`](../../android/app/src/main/kotlin/in/yash0/cd/transfer/FileSaver.kt)).

The Android signaling client is hard-coded to `cd.yash0.in:443` and PeerJS `/peerjs/`; therefore the current path requires Internet reachability for signaling even when both peers are on the same LAN ([`TransferProtocol.kt`](../../android/app/src/main/kotlin/in/yash0/cd/transfer/TransferProtocol.kt)). WebRTC may select a direct LAN candidate after signaling, but that is not an offline-LAN solution by itself.

The repository’s protocol documentation explicitly says v1 has no resume and a disconnected transfer fails ([`docs/cdx-v1-release-design.md`](../../docs/cdx-v1-release-design.md)). The Android implementation is a separate PeerJS/WebRTC path and does not inherit the CLI relay’s authenticated record protocol.

## Android lifecycle conclusions

* A transfer started from a visible user action can be kept active with a foreground service and an ongoing low-importance notification. Android’s background-start rule permits a foreground service when the app transitions from a user-visible state or the user acts on an app UI/notification; a background process cannot freely start one ([Android background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)). Start the service synchronously from the send/join action, before the activity can disappear.
* `dataSync` is a reasonable compatibility choice for the existing API 34 target, but it has a hard future limit. For apps targeting Android 15/API 35+, `dataSync` foreground services receive a combined six-hour-per-24-hour budget and `Service.onTimeout()`; failure to stop promptly can crash the process ([FGS timeout](https://developer.android.com/develop/background-work/services/fgs/timeout)). Implement `onTimeout()` and surface a resumable checkpoint before raising target SDK.
* Android 14 introduced user-initiated data-transfer jobs (UIDT). They are scheduled while the app is visible, begin promptly, show a notification, and can run for an extended period subject to system health; Android’s compatibility guidance recommends a foreground-service/WorkManager fallback below API 34 ([UIDT](https://developer.android.com/develop/background-work/background-tasks/uidt)). Use UIDT for a user-started internet download/upload when the transport is job-friendly. A live peer receiver that must accept an incoming LAN connection still needs a foreground service or a companion-device style relationship; UIDT is not a general daemon.
* WorkManager long-running workers are still implemented using a foreground service and remain subject to foreground-service/background-start constraints. Android 16 also warns that such workers can consume the app’s JobScheduler quota ([long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)). It is useful for retrying durable chunks after a disconnect, not for holding a perpetual listening socket.
* Doze suspends network access, ignores ordinary wakelocks, and defers jobs and alarms. A foreground service is an explicit exemption while it is active, but it is not permission to keep a silent always-on process. Android recommends FCM for cloud wakeups; FCM cannot wake a receiver over an Internet-free LAN ([Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)). Consequently, “both endpoints online, fully offline LAN, automatic fallback” is practical only while the receiver’s user-visible service is active, or when the receiver is a special companion-device deployment. It cannot be promised after force-stop/process death/Doze with no network wake channel.
* A `PARTIAL_WAKE_LOCK` alone is insufficient for Wi-Fi. Android documents `WifiLock` for transfers that must keep Wi-Fi awake and warns to hold it only for the active large transfer because it harms battery life ([WifiLock API](https://developer.android.com/reference/android/net/wifi/WifiManager.WifiLock)). Acquire it only after a transfer is accepted, release it on complete/failure, and avoid it while merely waiting for a peer.
* Use `ConnectivityManager.NetworkCallback` to react to network changes and bind sockets to the selected `Network`; do not poll. The callback reports availability, loss, and capability changes ([connectivity monitoring](https://developer.android.com/training/monitoring-device-state/connectivity-status-type)). Prefer a local validated route when present, then reconnect through the Internet relay when it appears. A local-only hotspot can provide a no-Internet LAN, but requires `NEARBY_WIFI_DEVICES` on API 33+ ([local-only hotspot](https://developer.android.com/develop/connectivity/wifi/localonlyhotspot)); it is an optional product mode, not a universal background wake mechanism.

## Proposed lifecycle and transport

1. On explicit send or receive, persist a transfer record before opening sockets: transfer ID, direction, peer identity, file metadata, destination URI, bytes committed, per-file hash/checkpoint, transport mode, and next retry time. Use a foreground `TransferService` owned by the record, not by Compose state. On service restart, reload the record and either resume from the last authenticated checkpoint or mark it recoverable for user retry.
2. Keep the notification visible for the entire active transfer. Waiting for a receiver should have a bounded idle timeout and no wakelock. Once paired, acquire a short-lived Wi-Fi lock only if the selected route is Wi-Fi and release it immediately after terminal confirmation.
3. Add a transport abstraction with (a) local discovery/direct LAN signaling, ideally mDNS or a user-provided local endpoint, and (b) the existing HTTPS/WebSocket relay as fallback. Both transports carry the same authenticated, ordered, acknowledged records. A relay fallback cannot make the offline LAN path work when no Internet exists; the local path must be independently discoverable.
4. Resume at file-chunk boundaries. The receiver must fsync/close each checkpoint or use a durable sparse/temp file before acknowledging it. Reconnect exchanges transfer ID, file index, committed offset/hash, and resumes only after the sender verifies the checkpoint. On cancellation, delete the temp file; on success, atomically publish it to MediaStore.
5. Auto-accept only after a cryptographic identity match. Clerk can provide authentication and organization/member roles, but Clerk membership is not itself a LAN proof. Cache a locally approved recipient/sender public key (or device key) and require a signed offer matching that key; show a one-time approval flow while online. Subsequent trusted offers can auto-accept offline. Clerk’s organization metadata supports custom attributes and can be placed in session claims, but claims have size/refresh limits ([metadata](https://clerk.com/docs/guides/organizations/metadata)); backend session verification can be performed without a live Clerk API call when the verifier has Clerk’s public key ([`authenticateRequest`](https://clerk.com/docs/reference/backend/authenticate-request)). This keeps Clerk as a free hosted bootstrap/control plane while making transfer admission local and durable.
6. If the app is force-stopped, Android has no supported way to restart it for a LAN offer. Report “offline receiver unavailable” to the sender and retry when the user opens the app or when an Internet wake path is available. Do not claim guaranteed background reception in this state.

Linux should use a user-level `systemd` service for the receiver/CLI companion: `Restart=on-failure`, bounded exponential reconnect, `After=network-online.target`/`Wants=network-online.target`, and a persistent spool/checkpoint directory. The service should stop cleanly on SIGTERM and resume from the checkpoint on restart. Linux power management still suspends radios/devices; no userspace service can guarantee transfer progress while the machine is asleep. Use systemd’s service and special-target definitions ([`systemd.service`](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [`systemd.special`](https://www.freedesktop.org/software/systemd/man/latest/systemd.special.html)) and measure suspend/resume separately.

## No-Google-Play and free-service constraints

The current barcode dependency is `com.google.mlkit:barcode-scanning`, the bundled model artifact. Google documents that bundled models are statically linked and available immediately; the Play-Services artifact is the unbundled alternative ([ML Kit Android barcode scanning](https://developers.google.com/ml-kit/vision/barcode-scanning/android)). This supports sideloaded/no-GMS scanning, subject to verifying the resolved dependency graph in the APK. The WebRTC and Java WebSocket dependencies are Maven artifacts and do not imply Google Play Services. Clerk and the CD relay remain optional Internet bootstrap/fallback services; offline LAN transfer must continue from cached keys and local discovery.

## Build and device evidence

The checkout contains the Gradle wrapper (`gradle-8.7`), Android Gradle Plugin 8.5.2, compile/target SDK 34, and a unit-test/lint/assemble command documented by the README. In this environment `adb`, `sdkmanager`, and `emulator` are absent and no `ANDROID_HOME`/`ANDROID_SDK_ROOT` is configured. The default `./gradlew testDebugUnitTest lintDebug assembleDebug` therefore fails before Gradle startup because the `mise` Java shim has no selected version. With the installed Temurin 17 path supplied explicitly, Gradle 8.7 starts and downloads its wrapper, but the combined build did not complete within the bounded attempt (it produced no task result before being interrupted). No device or emulator was available, so no battery, Doze, force-stop, LAN, or APK install claim is validated here.

Android’s official command-line tooling requires SDK packages plus `adb`, `avdmanager`, `sdkmanager`, and the emulator; `adb` installs/debugs APKs and captures logcat ([command-line tools](https://developer.android.com/tools), [build from command line](https://developer.android.com/build/building-cmdline)).

## Validation plan

Run on at least API 29, API 34, and API 35/36, with one physical no-GMS device and one emulator/physical device with Play Services; run the Linux receiver under systemd. Record exact APK SHA, OS/build, battery percentage, Wi-Fi/cellular state, and transfer IDs.

1. Baseline: 1 GiB and 10 GiB files on the same Wi-Fi, screen on/off, activity backgrounded, and charging/unplugged. Measure throughput, CPU, radio/battery drain, notification lifetime, and final SHA-256.
2. Lifecycle: lock screen, rotate/recreate activity, swipe task away, kill process, force-stop, reboot, and let the service hit its timeout. Expected: active foreground transfer survives activity/task removal; force-stop and reboot require explicit recovery; no silent data loss.
3. Power: `adb shell dumpsys deviceidle force-idle`, exit idle, screen off for 30 minutes, and test Wi-Fi lock only during transfer. Expected: active foreground transfer completes; waiting mode consumes no wakelock; Doze limitation is surfaced.
4. Route: no-Internet local-only hotspot/direct LAN, Internet relay, LAN loss then Internet return, Internet loss with LAN retained, and captive portal. Expected: local mode transfers without the relay; fallback reconnects without duplicate bytes; a route change never bypasses authentication.
5. Resume/admission: kill either endpoint at chunk boundaries, corrupt/replay a chunk, offer from an untrusted key, and offer from a cached trusted key while offline. Expected: exact resume from durable checkpoint, rejection of altered/replayed data, auto-accept only for the cached key.
6. Linux: suspend/resume, network reorder, daemon restart, disk-full, and SIGTERM. Expected: checkpointed restart, bounded retry, no partial file publication, and a clear terminal status.

Battery success should be expressed as a measured budget (for example, idle waiting delta over 30 minutes and transfer energy per GiB on each device), not as a promise derived from a wakelock API.

## Constraints / issues

* **PASS:** user-initiated foreground transfers, bounded battery behavior, streaming MediaStore output, no-GMS bundled scanning, free Clerk/relay bootstrap, and Linux service supervision are implementable.
* **ISSUES:** current Android signaling is Internet-dependent; current service state is not durable; current protocol has no resume; `START_STICKY` can restart an empty service; no `onTimeout()` handling; no local discovery; no trusted-key admission; target SDK 34 must be exercised against newer OS behavior.
* **BLOCKED:** guaranteed unattended offline-LAN reception after force-stop/process death or Doze without a visible foreground service, companion-device privilege, or another OS wake path. This is an Android platform constraint, not a missing library.

# Transfer transport options

Research checked 2026-09-25. This is a design comparison for the [CD highway acceptance checks](highway-acceptance.md) and [issue #9](https://github.com/YashasVM/cd/issues/9), not a decision to replace the current transport. Issue #9 leaves TCP versus QUIC open for an interoperability spike.

## What CD has today

Browser sharing uses PeerJS and a WebRTC data channel with CD's Worker for signaling. The Android client uses native WebRTC against that path. `cdx send` uses a separate encrypted WebSocket protocol through a Cloudflare Durable Object; it sends one file and has no resume support. The relay does not retain file data. See [README](../README.md), [agent transfer v1](agent-transfer-v1.md), and [release design](cdx-v1-release-design.md).

The browser code's two-word code selects a PeerJS ID from 121², or 14,641, values. The sender accepts the first connecting peer and starts sending when its channel opens. This code is a rendezvous address, not strong authorization or an authenticated peer identity. The CLI link has a separate random 256-bit fragment key and authenticated records. See [`p2p-code.js`](../src/p2p-code.js), [`main.js`](../src/main.js), and [agent transfer v1](agent-transfer-v1.md).

The highway requires offline LAN transfers after enrollment, live endpoints without stored server copies, verified resume after reconnect and process restart, and direct internet connections with a relay fallback. Paid usage is prohibited. No single transport supplies device trust, local discovery, durable checkpoints, multi-file completion, or correct progress accounting. Those belong in a shared transfer protocol above the route: authenticated sender and recipient identities; a manifest with one stable ID, size, and digest per file; acknowledged verified chunks; retained receiver checkpoints; source-change checks; and a final receipt only after every selected file is verified. [Acceptance checks](highway-acceptance.md) define the observable behavior.

## Options

| Route | Advantages | Limits and operating cost | Fit for CD |
| --- | --- | --- | --- |
| **WebRTC data channel, direct with TURN fallback** | Browser-native peer transport. ICE tests network paths and can use TURN when direct connectivity fails. Data channels provide reliable and ordered delivery and DTLS protection; a sender can use `bufferedAmountLowThreshold` for flow control. [WebRTC connection guide](https://webrtc.org/getting-started/peer-connections), [RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html), [WebRTC data channel flow control](https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel/bufferedAmountLowThreshold). | Signaling is a separate service. TURN carries the full file traffic when relaying, so reliable internet fallback needs relay capacity and a quota policy. WebRTC does not persist application chunks after a process dies. [WebRTC signaling](https://webrtc.org/getting-started/peer-connections), [TURN guide](https://webrtc.org/getting-started/turn-server). | Best browser-compatible direct path. Add authenticated signaling and an application resume protocol; provide local discovery for WAN-free LAN use. |
| **TLS WebSocket relay** | Works in standard browsers and native clients; CD already has a live encrypted relay implementation. A single server path avoids peer NAT setup failures. Cloudflare Durable Objects support hibernating WebSocket connections. [WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API), [Durable Object WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/). | The server forwards every byte, adds a network hop, and is required during the transfer. The browser `WebSocket` API has no automatic backpressure, so CD must keep its own bounded acknowledgement window. Cloudflare Free quotas can fail once exceeded. A hosted relay cannot provide offline LAN service. [WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API), [Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/). | Good internet fallback and useful baseline, but not the only route. Keep end-to-end record encryption and add restartable checkpoints. |
| **HTTP resumable upload and download, such as tus plus Range** | tus defines upload offsets, optional checksums and expiration. HTTP Range supports partial downloads. Familiar HTTP infrastructure and explicit offsets simplify retry logic. [tus protocol](https://tus.io/protocols/resumable-upload), [HTTP Range](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests). | Conventional upload and download stages a server copy, contrary to the current live-only requirement. A live HTTP proxy could avoid storage but would need its own pairing, backpressure, retry, and receiver checkpoint design. tus upload offsets alone do not prove the receiver saved the bytes. | Choose this only if the product accepts temporary encrypted server storage, or use HTTP directly between native LAN endpoints with a separately designed receive API. |
| **S3-style multipart object storage** | Independent parts can be retried or uploaded in parallel, and the service can list uploaded parts. [S3 multipart overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html). | It stores a server copy, requires cleanup of unfinished parts, and adds storage and request accounting. S3's multipart ETag is not necessarily a whole-file MD5 digest. Cloudflare R2 has a free allowance, but usage above it is billable; a free allowance does not meet a strict no-paid-usage rule by itself. [S3 multipart overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [R2 pricing](https://developers.cloudflare.com/r2/pricing/). | Useful only if delayed delivery becomes an explicit product requirement and a hard storage quota can be enforced. |
| **WebTransport over HTTP/3** | Browser API provides reliable streams with backpressure and separate unreliable datagrams. Multiple streams could isolate file and control traffic. [W3C WebTransport](https://www.w3.org/TR/webtransport/), [Mozilla WebTransport API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API). | It is a browser-to-server API, so peer transfer still needs a forwarding server. It is newly baseline in 2026 and older browsers remain a concern. It requires a compatible HTTP/3 server and still needs application-level resume and identity. [W3C WebTransport](https://www.w3.org/TR/webtransport/), [Mozilla WebTransport API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API). | Candidate for a later relay benchmark, not a prerequisite for reliable transfers now. Do not assume the current Durable Object relay can accept WebTransport sessions. |
| **Native QUIC or TCP direct path** | Native clients can implement a local listener and avoid a cloud data hop on LAN. QUIC has multiplexed reliable streams and can survive some client address changes through connection migration. [RFC 9000](https://www.rfc-editor.org/info/rfc9000/). | Ordinary browser pages cannot open raw TCP or UDP sockets. QUIC does not provide NAT traversal, peer discovery, authorization, or durable resume. Native protocol maintenance increases when the browser still needs a different route. [Chrome Direct Sockets scope](https://developer.chrome.com/docs/iwa/direct-sockets), [RFC 9000](https://www.rfc-editor.org/info/rfc9000/). | Reasonable native-to-native LAN optimization after a shared transfer contract exists; it cannot replace WebRTC or a browser-compatible server route for all clients. |

## Recommended choice

Keep WebRTC for browser-compatible direct transfer and add an explicit, quota-bounded relay fallback. Reuse the current encrypted WebSocket relay first because it already runs in CD, then benchmark managed TURN against it on real separate-network transfers. Use the same authenticated manifest, chunk IDs, verified checkpoints, and final receipt over both routes. A route change should negotiate retained chunks and continue the transfer instead of creating a new file or claiming completion early. Add authenticated local discovery and a local route so enrolled devices can transfer with WAN access disconnected. For native-to-native LAN transfers, run the TCP versus QUIC interoperability spike before choosing either one. This is a proposed design based on the acceptance checks and route properties above, not a measured speed claim.

For TURN, Cloudflare currently lists a 1,000 GB monthly free allowance shared with Realtime SFU and $0.05 per GB after that; STUN is free. It also documents TURN over UDP, TCP, and TLS. The allowance is useful for evaluation, but the highway's no-paid-usage rule needs a verified hard cap or an explicit stop before overage. [Cloudflare TURN FAQ](https://developers.cloudflare.com/realtime/turn/faq/), [TURN service](https://developers.cloudflare.com/realtime/turn/), [Realtime pricing](https://developers.cloudflare.com/realtime/sfu/platform/pricing/). Check these plan terms again before deployment.

Transport selection should follow measured direct-connect rate, transfer throughput, memory use, battery use, and resume success on Android, Linux, and target browsers. Measure complete transfers and the exact files saved, including a five-file batch and a route change. A faster transport cannot repair missing file-level acknowledgements or a guessed progress counter.

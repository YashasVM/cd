The largest confirmed bottlenecks are in resumable transfers. The best first changes are to pipeline chunks and replace the browser's repeated file-commit cycle. Browser hashing is a separate CPU limit. A complete Rust rewrite has no measured justification from this audit.

Measured on this checkout on 17 October 2026. All speeds below are MiB/s. Improvements to isolated operations are not whole-app speedup promises.

Priority 1 · confirmed protocol limit

Resume waits an entire round trip after every 256 KiB

At 300 ms of added ACK round-trip delay, ordinary CLI transfers measured 7.98 MiB/s; resumable transfers measured 0.72 MiB/s. Each result is the median of three verified 8 MiB transfers through the same local proxy. This compares existing modes, not a before-and-after fix.

Send multiple chunks within a bounded window and acknowledge committed progress cumulatively. Keep acknowledgements behind durable storage. This needs compatible protocol negotiation and crash/restart verification.

Priority 2 · confirmed storage overhead · prototype tested

Browser resume repeatedly reopens the growing staging file

It calls createWritable({keepExistingData:true}), writes 256 KiB, and closes the file for every chunk. This API preserves the old contents through a temporary file. The repeated preservation creates increasing work as the file grows. See the API documentation.

Priority 3 · confirmed CPU limit · replacement unmeasured

The incremental browser SHA-256 is slow

The current hasher processed a median 38.84 MiB/s, or 7.86 MiB/s with 4× renderer CPU throttling. Three runs per setting processed 16 MiB and checked the digest against WebCrypto.

Benchmark a faster bounded-memory implementation and move hashing off the UI thread. This is a reasonable place to test WASM, including Rust compiled to WASM. There is no measured Rust or WASM speedup yet.

Source: src/incremental-sha256.js. It allocates a new schedule array for every 64-byte block. Resume also hashes before sending, during sending, and rechecks the staged file on receipt. Native WebCrypto measured 993.79 MiB/s for a full 16 MiB buffer, but does not support streaming input; loading whole large files into memory is not an equivalent replacement.

The early CLI/browser difference is worth profiling, but these measurements do not identify its root cause. Browser source reads, serial async crypto/storage calls, buffer polling, record copying, and SCTP need separate profiles. The pure-JS resume hasher is not used by ordinary v1 transfers, so it does not explain that gap.

CLI resume performs a staging-file sync, checkpoint-file sync, and directory sync for each chunk. Batching these barriers is a candidate, but the real-disk run did not isolate their cost. Do not claim a measured fsync speedup.

The ordinary send windows also have finite throughput ceilings on high-delay links. Larger windows require measurement against the relay's 32 MiB buffer limit. Increasing buffers without bounds can turn throughput problems into memory failures.

Direct transfer setup can delay the first offer while gathering candidates. Folder preparation, large-file memory use, startup, production relay geography, multi-transfer concurrency, packet loss, mobile hardware, Safari, and Firefox remain unmeasured here. No finding establishes that the application can never be a bottleneck.

Reproduce and assess the evidence

Intel i5-13420H, Linux amd64, Go 1.26.8, Node 26.10.0, local Wrangler and Chromium. The checkout contains pre-existing uncommitted changes. Source fingerprints and exact environment details accompany the raw JSON files.

The first relay baseline was less loaded. Emulator and Java activity increased later host load substantially. Do not treat rates from different invocations as controlled comparisons. CPU throttling is an emulation setting, not a real phone benchmark; native I/O and worker work need not scale by the same factor.

The network audit delays every complete WebSocket message independently by 0, 25, or 75 ms per proxy hop. Four hops add 0, 100, or 300 ms to a payload/ACK round trip. Payloads are incompressible random bytes, and complete received files are SHA-256 checked. Browser microbenchmarks use a random 256 KiB block repeated to 16 MiB. Prototype results verify actual OPFS bytes; they are not full transfers.

An initial proxy mishandled close ordering, and another early invocation exceeded the local connection admission limit; those runs are retained separately as invalid measurements.
